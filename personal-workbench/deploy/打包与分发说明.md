# 打包与分发说明

> 项目：个人工作台 personal-workbench
> 脚本：`deploy/build_packages.py`
> 本说明面向「拿到这份代码、需要自己生成交付包」的人。

---

## 0. 结论先行

一条命令产出两个 ZIP：

```bash
python deploy/build_packages.py --version 1.0.4
```

| 产物 | 用途 | 区别 |
|---|---|---|
| `personal-workbench-v<版本>-clean-win.zip` | **发给同事** | `data/` 为空，首次启动进入配置向导 |
| `personal-workbench-v<版本>-data-win.zip` | **自己换机/本机使用** | `data/` 内置真实数据，解压即是原状态 |

两个包都是 **Windows 免安装包**形态：自带裁剪好的 JRE 8，目标机不需要装
Java / Maven / Node / Docker，解压后双击 `start-workbench.cmd` 即可。

> 为什么“解压即用”不用 Docker 实现：Docker 版要求目标机先装 Docker Desktop
> （约 1.2GB 安装包 + WSL2/Hyper-V + 通常需重启一次）。免安装包把这个前置条件
> 降为零。包内仍附带了 `docker/` 目录作为**可选**跑法，见 §6。

## 1. 前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| Python | 3.8+ | 只用标准库，**不需要 pip install 任何东西** |
| Docker Desktop | 需要时 | 仅当要构建 jar 时；`--skip-build` 可绕过 |
| 裁剪好的 JRE 8 | 必须有 | 默认读 `dist/runtime/`，可用 `--jre-source` 指定 |

### JRE 8 从哪来

Java 8 **没有 jlink**（JEP 282 是 Java 9 才引入的），运行时无法自动生成，必须预先裁剪：

1. 下载 **Eclipse Temurin JRE 8** 的 zip 版（不要安装包）并解压
2. 按 `docs/开发文档-Java8版.md` §0.4 的裁剪清单删文件，目标约 70 MB 未压缩
3. 放到 `dist/runtime/`，后续每次构建直接复用

脚本会校验 `runtime/bin/java.exe` 存在且 `java -version` 输出含 `1.8`，不符合直接拒绝出包。

## 2. 常用命令

```bash
# 最常用：构建最新 jar + 出两个包
python deploy/build_packages.py --version 1.0.4

# jar 已经新鲜，跳过 Maven（本地迭代快很多，约 30 秒）
python deploy/build_packages.py --version 1.0.4 --skip-build

# 只出干净包（不读、不碰个人数据）
python deploy/build_packages.py --version 1.0.4 --only clean

# 只出含数据包
python deploy/build_packages.py --version 1.0.4 --only data

# 数据不在默认位置
python deploy/build_packages.py --version 1.0.4 --data-dir D:\my-data

# 复用别处的 JRE 8
python deploy/build_packages.py --version 1.0.4 --jre-source D:\cache\jre8-trimmed
```

### 参数表

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--version` | **必填** | 版本号，写进文件名、`app/VERSION`、包内说明 |
| `--root` | 脚本上一级 | 项目根目录 |
| `--out-dir` | `<root>/dist` | 产物输出目录 |
| `--data-dir` | `<root>/dev-data` | 含数据包的数据来源 |
| `--jre-source` | `<root>/dist/runtime` | 裁剪好的 JRE 8 |
| `--package-name` | `personal-workbench` | 包内根目录名 |
| `--only` | `both` | `clean` / `data` / `both` |
| `--skip-build` | 关 | 跳过 Maven，复用现有 `server/target/workbench.jar` |
| `--skip-jre` | 关 | 不打自带 JRE（产出的包将依赖目标机有 Java 8） |
| `--build-image` | `personal-workbench-dev:java8` | 用于 Maven 构建的镜像 |
| `--maven-volume` | `workbench-maven-repo` | Maven 本地仓库卷名（复用可大幅加速） |
| `--compresslevel` | `6` | zip 压缩级别 0–9 |

## 3. 脚本内置的 5 道硬校验

这些校验的存在意义是「宁可构建失败，也不产出坏包」：

1. **字节码校验** —— jar 主类必须是 major version 52（Java 8）。防止误用高版本 JDK 编译导致目标机跑不起来。
2. **前端新鲜度校验** —— 把 jar 内的 `static/` 资源与 `server/src/main/resources/static/` 逐字节比对。
   任何不一致（缺失或内容过期）都直接失败。
   *这一条是为了防住「jar 是旧版本构建的、前端页面还是老样子」——本项目真实踩过：
   曾出现 jar 内 `app.js` 只有 41KB 而源码已 272KB、`poems.js` 完全缺失的情况。*
3. **运行时校验** —— `runtime/bin/java.exe` 必须存在且版本为 1.8。
4. **干净包硬校验** —— 压缩前断言包内**不存在**任何 `*.db / *.db-wal / *.db-shm / *.log / *.gz`，
   且文本文件中不含 `sk-****`、`password_hash`、`"api_key":"..."` 之类的凭据特征。
   命中任何一条即中止构建。
5. **含数据包校验** —— `data/workbench.db` 必须存在且非空，否则中止。

数据本身走 **SQLite `VACUUM INTO`** 生成一致性快照（等价于应用内「在线备份」），
而不是直接复制 `workbench.db / -wal / -shm` 三件套 —— 后者在 WAL 模式下可能得到
不一致快照。快照生成后会跑 `PRAGMA integrity_check` 并打印各表行数。

## 4. 包结构

```
personal-workbench/
├── start-workbench.cmd        ← 双击启动
├── stop-workbench.cmd         ← 双击停止
├── backup-workbench.cmd       ← 双击备份
├── 使用说明.txt               ← 给最终用户看的
├── 版本说明.txt               ← 标明这是干净包还是含数据包（脚本生成）
├── .dockerignore
├── app/
│   ├── workbench.jar          ← 后端 + 前端静态资源
│   └── VERSION
├── config/
│   └── application.yml        ← 端口 / 数据目录 / 时区，不含任何密钥
├── data/                      ← 唯一需要备份的目录
│   ├── workbench.db           ← clean 包为空；data 包内置快照
│   ├── attachments/
│   ├── backups/
│   └── vault-index.json       ← 仅 data 包
├── docker/                    ← 可选的容器跑法
│   ├── Dockerfile
│   ├── docker-compose.yml
│   └── 说明.txt
├── logs/
├── runtime/                   ← 自带裁剪 JRE 8（约 94 MB 未压缩）
└── scripts/
    └── launcher.ps1           ← 全部启动逻辑
```

产物旁会生成 `.sha256` 文件，校验方式：

```powershell
Get-FileHash .\personal-workbench-v1.0.4-clean-win.zip -Algorithm SHA256
```

## 5. 给最终用户的交付注意事项

* 建议解压到 **D 盘根目录**（如 `D:\personal-workbench`）。
  **不要**放桌面、`C:\Program Files`、OneDrive 或任何自动同步目录 ——
  同步软件会锁住 `workbench.db-wal`，可能导致启动失败或数据损坏。
* 杀毒软件（火绒 / 360 / Defender）可能拦截「java.exe 监听端口 + 自写启动器」，
  被拦时把整个文件夹加入信任区。
* 端口默认 `18080`，被占用时改 `config/application.yml` 里的 `server.port`。
* **含数据包请勿外发**：里面有真实数据，可能包含账号口令与 AI API Key。

## 6. 可选的 Docker 跑法

包内 `docker/` 目录是给「目标机已经装了 Docker Desktop」的场景准备的备选：

```bash
cd docker
docker compose up -d --build      # 首次构建并后台启动
docker compose logs -f
docker compose down
```

* 端口：宿主机 `18080` → 容器 `8080`，改 `docker-compose.yml` 的 `ports` 即可
* 数据：挂载包目录下的 `data/`，容器重建不丢数据
* 基础镜像：默认 `eclipse-temurin:8-jre`（需联网拉取）；
  若目标机无法联网，在同目录建 `.env` 写入本机已有的 Java 8 镜像：

  ```
  BASE_IMAGE=<你的镜像>:<标签>
  ```

## 7. 排错

| 现象 | 原因与处理 |
|---|---|
| `未找到 jar` | 去掉 `--skip-build`，或先手动跑一次 Maven 构建 |
| `前端资源与源码不一致` | jar 是旧版本构建的。去掉 `--skip-build` 重新构建 |
| `runtime\bin\java.exe 不存在` | JRE 8 未裁剪/未就位，见 §1 |
| `runtime 里的 Java 不是 1.8` | 放错版本了，换成 JRE 8 |
| `干净包内发现数据库/日志残留` | 属预期保护。检查 `deploy/` 或模板里是否混入了个人文件 |
| Docker 内 Maven 打包失败 | 看日志末尾的 Maven 输出；确认 `--build-image` 指向的镜像存在 |
| 容器起来了，宿主机访问却报 `Empty reply from server`（curl rc=52） | 容器里 Tomcat 绑到了 `127.0.0.1`。包内 `config/application.yml` 面向**免安装包**，绑的是回环地址；在容器里这只等于绑容器自己的回环，端口映射只能拿到空响应。Dockerfile 的 ENTRYPOINT 已用 `--server.address=0.0.0.0` 覆盖 —— **改 ENTRYPOINT 时别把这条删掉**。判据：`netstat` 有 LISTENING、`docker ps` 的 PORTS 正常，就直接查应用配置里的监听地址，不要再折腾 Docker 网络 |
| 沙箱/受限环境下删目录被拦截 | 脚本在 Windows 上优先用 `cmd /c rd /s /q` 删除 stage，与 `build-release.ps1` 的做法一致 |

构建日志落在 `<out-dir>/build-packages.log`。

## 8. 与 `build-release.ps1` 的关系

`deploy/build-release.ps1` 是更早的 PowerShell 版本，**只产出干净包**，
且存在「不校验 jar 里的前端是否为最新」的缺口（见 §3 第 2 条）。

**自 v1.0.4 起，打包以 `deploy/build_packages.py` 为准**，两个包都由它产出。
`build-release.ps1` 保留仅为兼容旧命令，不再新增功能。
