## 0. 决策摘要

用户已拍板四项：

| 项 | 决策 | 影响 |
|---|---|---|
| 解析执行方式 | **异步** | 需新建异步基础设施（项目当前没有） |
| 视觉模型 | **外部服务** | 复用 `ai.base_url` / `ai.api_key`，新增 `ai.vision_model` |
| `rawText` | **落库** | 进 `inbox_item.raw_content`，会被全局搜索命中 |
| 范围 | **四个入口全做** | 收录 / 任务 / 日程 / 收藏 |

### 0.1 调研发现的三个既有冲突（必须先解决）

这三条不是新需求带来的，是既有代码与「图片解析」这个新场景相撞产生的，**不解决则功能必然是错的**。

**冲突一：`confirmHighConfidence()` 会绕过人工确认**

```java
// InboxService.java L145-164
double AUTO_CONFIRM_THRESHOLD = 0.70;
for (InboxRecord record : inboxRepository.findByStatus("processed")) {
    if (record.aiConfidence == null || record.aiConfidence.doubleValue() < AUTO_CONFIRM_THRESHOLD) continue;
    ...
    results.add(confirm(record.id, request));
}
```

这个入口按 0.70 阈值**自动落库**。视觉模型对结构清晰的截图（如邮件）置信度轻松超过 0.70，结果是：**用户传了张邮件截图，还没看到解析结果，任务就已经被建好了。**

而图片解析恰恰是最需要人工过目的场景——模型读错一个日期、把对方的话当成我的承诺，都会产生一条看起来正常但内容错误的任务。

→ 解决：新增 `inbox_item.origin` 列，图片条目**排除在批量自动确认之外**。

**冲突二：`raw_content` 有 4000 字硬上限**

```java
// InboxService.java L240-244
private String requireRaw(String raw) {
    if (value.isEmpty() || value.length() > 4000)
        throw new BizException(ErrorCode.INVALID_PARAMETER, "收录内容不能为空，且不能超过 4000 字");
```

视觉抽取的 `rawText`（聊天记录全文）落库前必须 ≤4000 字。长对话截图会超，而这是一个**硬校验**，超了直接抛异常 —— 表现是「图传上去了但整个收录失败」。

→ 解决：落库前截断到 4000，`ai_payload.rawTruncated = true` 标记，界面提示「截图内容过长，已保留前 4000 字」。

**冲突三：`confirm()` 一次只能落一条实体**

```java
// InboxService.java L107-135
public ConfirmResultVO confirm(long id, InboxConfirmRequest request) {
    ...
    if ("archived".equals(record.status)) {
        Long existing = findExistingEntity(id, request.getCategory());
        if (existing != null) return new ConfirmResultVO(...);
        throw new BizException(...);   // ← 第二次调用走这里，抛异常
    }
```

`InboxConfirmRequest` 全是标量字段（title / due / priority / start / end / eventType / repeatWeeks），结构上就是「一个条目 → 一个实体」。而一张聊天记录截图里经常有 2–3 件事。

**不能靠重复调 `confirm` 实现多条目**：第一次调用会把记录 `markArchived`，第二次进 `archived` 分支后 `findExistingEntity` 按 category 查不到（第二次的 category 与第一次不同）就抛异常。

→ 解决：新增批量确认接口 `POST /api/v1/inbox/{id}/confirm-items`，一次事务内落多条。

## 1. 核心设计判断

### 1.1 四个入口全做，但**不是四入口同构**

这是本方案最重要的设计判断。

用户在**表单里**上传图片时，他已经在表达「我要建什么」了。此时再弹一个确认页问「这张图是任务还是日程」是多余的，而且会打断他正在填的表单。

所以两条链路分开：

| 入口 | 图片的作用 | 是否需要确认页 |
|---|---|---|
| **收录页** | 完整解析 + 分类 | ✅ 需要（多条目确认页） |
| **任务表单** | 抽取字段**预填**表单 | ❌ 不需要（表单本身即确认界面） |
| **日程表单** | 抽取字段**预填**表单 | ❌ 不需要 |
| **收藏表单** | 抽取正文**预填**表单 | ❌ 不需要 |

这个划分带来两个直接收益：

1. **工作量大幅下降**：确认页只需处理收录页一种形态，不用处理「四种落点 × 各自字段」的组合。
2. **交互更自然**：表单里的图更像「帮我填一下」，收录页的图更像「帮我读一下」。

**判据说清楚**：表单入口往表单里**填值**（用户可见可改），收录入口往收集箱里**建条目**（需要用户判断对不对）。前者用户天然在核验，后者需要专门设计核验界面。

### 1.2 抽取结果必须携带「来源标记」

模型输出的每个字段要标明它是**读出来的**还是**推出来的**：

- `extracted`：图上明确写了（如「9月20日前」）
- `inferred`：模型推算的（如「明天下午」→ 具体日期）
- `missing`：图上没有，字段留空

**这不是装饰，是责任划分。** 标 `extracted` 的错了是模型的锅，标 `inferred` 的需要用户确认。界面上必须视觉可区分。

对齐既有原则：**任何方向都不隐式补今天**。截图里没提时间就不给 `due`，给了反而是污染（会看到一堆「今天到期」的假任务）。

### 1.3 只做单图解析，不做多图联合推理

一期明确只做「一张图 → 一组草稿」。多张截图拼出一件事（如聊天记录翻页）复杂度陡增，且无法界定「几张算一组」。

一条记录可挂多张图，但**只有一张参与解析**（第一张，界面上标明「已解析」）。

## 2. 数据模型

### 2.1 V10 迁移

```sql
-- V10__attachment_and_image_origin.sql

-- ① 附件表：多态外键，四个实体共用一张表
CREATE TABLE attachment (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_type    TEXT,
    owner_id      INTEGER,
    file_name     TEXT NOT NULL,
    original_name TEXT,
    mime_type     TEXT NOT NULL,
    byte_size     INTEGER NOT NULL,
    width         INTEGER,
    height        INTEGER,
    sha256        TEXT NOT NULL,
    sort_order    INTEGER NOT NULL DEFAULT 0,
    created_at    TEXT NOT NULL,
    updated_at    TEXT,
    deleted       INTEGER NOT NULL DEFAULT 0,
    deleted_at    TEXT,
    CONSTRAINT chk_attachment_owner_type CHECK (
        owner_type IS NULL OR owner_type IN
        ('task','schedule_event','favorite','knowledge_note','inbox_item')
    ),
    CONSTRAINT chk_attachment_owner_pair CHECK (
        (owner_type IS NULL AND owner_id IS NULL)
        OR (owner_type IS NOT NULL AND owner_id IS NOT NULL)
    ),
    CONSTRAINT chk_attachment_deleted_at CHECK (deleted_at IS NULL OR deleted = 1)
);

CREATE INDEX idx_attachment_owner  ON attachment(owner_type, owner_id) WHERE deleted = 0;
CREATE INDEX idx_attachment_sha256 ON attachment(sha256);
CREATE INDEX idx_attachment_orphan ON attachment(created_at) WHERE owner_id IS NULL AND deleted = 0;

-- ② 收录来源标记：图片条目排除在批量自动确认之外（冲突一）
ALTER TABLE inbox_item ADD COLUMN origin TEXT NOT NULL DEFAULT 'text';

-- ③ 解析状态：图片解析是异步的，需要独立于 status 的进度标记
ALTER TABLE inbox_item ADD COLUMN parse_status TEXT;

-- ④ 视觉模型配置（同一个 base_url 下文本与视觉模型通常不同名）
INSERT OR IGNORE INTO app_config(config_key, config_value) VALUES
    ('ai.vision_model', ''),
    ('ai.vision_enabled', 'false');
```

**为什么是 `ALTER TABLE ADD COLUMN`**：本迁移**没有**改动任何 `CHECK` 或 `NOT NULL` 约束，全部是加列与建新表，不需要「建新表→搬数据→DROP→RENAME」那套重活。这是 V9 已经确立的判据（「只加列用 ALTER，改 CHECK / NOT NULL 才整表重建」）。

### 2.2 明确不做的表改动

| 不动 | 理由 |
|---|---|
| `inbox_item.content_type` 的 CHECK | 现只允许 `text\|voice`。**图片不是 contentType，是附件**——收录仍是一条文本记录，图挂在它下面。改 CHECK 要整表重建，收益为零。 |
| `inbox_item.audio_path` | 语义是语音，图片混用会造成歧义。保持它空着。 |
| `task` / `schedule_event` / `favorite` / `knowledge_note` 四张表 | 一张都不改。附件经 `attachment.owner_type/owner_id` 反向关联，实体表保持纯净，也让「删实体级联软删附件」能集中在一处实现。 |

### 2.3 字段语义（显式，不留隐式兜底）

| 字段 | 取值 | 语义 |
|---|---|---|
| `attachment.owner_type` | `NULL` | **明确的「待绑定」状态**，不是垃圾数据。用户传了图还没提交表单时就是这个状态。 |
| `inbox_item.origin` | `text` / `image` | `image` = 本条目来自图片解析，**不参与批量自动确认** |
| `inbox_item.parse_status` | `NULL` / `running` / `success` / `failed` | 图片解析进度。文本条目恒为 `NULL`（不适用，而非「未开始」） |

**`parse_status` 与 `status` 的区别必须说清**：`status` 是收录条目的生命周期（pending/processed/failed/archived），`parse_status` 只描述「视觉解析」这一步。二者独立：解析失败时 `status='pending'` + `parse_status='failed'`，条目仍在收集箱里等用户手动补文本。

## 3. 接口契约

### 3.1 新增接口一览

```
POST   /api/v1/attachments                     上传单个文件（multipart/form-data, field=file）
GET    /api/v1/attachments/{id}/raw             读取原图（流式）
DELETE /api/v1/attachments/{id}                 软删
GET    /api/v1/attachments?ownerType=&ownerId=  按实体查附件

POST   /api/v1/inbox/{id}/parse                 触发图片解析（异步，返回 jobId）
POST   /api/v1/inbox/{id}/confirm-items         批量确认（一次落多条实体）
GET    /api/v1/inbox/{id}/items                 取解析出的草稿列表
```

### 3.2 上传：单文件而非多文件

前端已支持多选，但**循环调用单文件接口**。理由：每张图独立进度、独立失败重试、单张失败不拖垮其余。多文件接口在这三点上都要额外设计。

响应：

```json
{
  "id": 12,
  "url": "/api/v1/attachments/12/raw",
  "originalName": "聊天记录.png",
  "mimeType": "image/png",
  "byteSize": 842133,
  "width": 1280,
  "height": 720,
  "sha256": "a3f1b2c3...",
  "deduped": false
}
```

`sha256` 命中已存在的附件时返回既有 id 并置 `deduped: true`，不重复占盘。

### 3.3 上传通道独立于 `api.js`

`api.js` 的 `request()` **硬编码 `Content-Type: application/json`**，不能复用。新增独立的 `uploadFile(file)` 函数：

```javascript
// api.js 新增，不改造既有 request()
async function uploadFile(file, onProgress) {
  const form = new FormData();
  form.append("file", file);
  return request("/api/v1/attachments", {
    method: "POST", body: form, rawBody: true   // rawBody 跳过 JSON 头
  });
}
```

**硬约束：既有 11 个 JSON 接口的行为不能有任何变化。** `rawBody` 是新增的可选开关，缺省走原路径。

### 3.4 批量确认接口

```java
// InboxConfirmItemsRequest
public class InboxConfirmItemsRequest {
    @NotEmpty(message = "至少选择一条")
    @Size(max = 5, message = "一次最多确认 5 条")

    public static class InboxConfirmItem {
        @NotBlank @Pattern(regexp = "task|schedule|favorite|knowledge", message = "...")

        private String title;
        @Pattern(regexp = "^$|\\d{4}-\\d{2}-\\d{2}", message = "日期格式不正确，请按 YYYY-MM-DD 填写")
        private String due;

```

**为什么上限是 5**：超过 5 件事说明这是长对话截图，应该进知识库当资料，而不是硬拆成 12 个任务。上限与前端 `MAX_ITEMS = 5` 常量对齐。

校验注解的中文 `message` 与 `InboxConfirmRequest` **逐字一致**——同一约束在不同入口必须给同一个提示。

## 4. 异步执行模型

### 4.1 现状：项目没有真正的异步

```java
// AiJobService.java L32-52
@Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
public long startClassifyJob() {
    long jobId = aiJobRepository.insertPending("classify", null, now);
    aiJobRepository.markRunning(jobId, now);
    inboxService.classifyPending();          // ← 同步执行完才返回
    aiJobRepository.markSuccess(jobId, ...);
    return jobId;
}
```

叫 job，实为同步——`insertPending → markRunning → 干活 → markSuccess` 全在一个方法里跑完才返回 `jobId`。前端拿到 id 时活已经干完了。

全项目搜索 `@Async` / `TaskExecutor` / `ExecutorService` 的结果：**零**。只有一个 `@Scheduled`（`DailyBackupScheduler`）和一个关服务用的裸 `new Thread`（`SystemService`）。

所以「异步解析」需要**新建基础设施**——这一点比表面看起来的量大。

### 4.2 关键约束：SQLite 只给了 4 个连接

```java
// DataSourceConfig.java L30-48
config.setJournalMode(SQLiteConfig.JournalMode.WAL);
config.setBusyTimeout(5000);
hikari.setMaximumPoolSize(4);   // 注释：Windows 下句柄开销大，刻意压小
```

- WAL：多读单写，读不阻塞写 ✅
- `busy_timeout=5000`：写冲突最多等 5 秒，超时抛 `SQLITE_BUSY`
- 池只有 4：并发度必须压住

→ **解析线程池必须是单线程**（`corePoolSize=1, maxPoolSize=1`）。串行处理，不并发。

实际使用量也支撑这个选择：每天手动操作上限 3 小时，不会有几十张图同时解析。串行的延迟完全可接受。

### 4.3 硬约束：调模型时不能持有写事务

这是最容易踩的坑，也是本设计里唯一一条「踩了会让整个系统卡死」的规则。

```
❌ 错误：一个大事务包住「调模型 + 写结果」
   BEGIN → HTTP 调视觉模型（3–10 秒）→ UPDATE → COMMIT
   → 这 10 秒里 SQLite 写锁被独占，所有其他写入排队，
     5 秒后全部 SQLITE_BUSY 失败

✅ 正确：事务边界切碎
   UPDATE parse_status='running'  （短写事务，立即提交）
   → 调视觉模型（无事务）
   → UPDATE 写结果                  （短写事务，立即提交）
```

实现上：**异步任务方法不能带 `@Transactional`**，改为在需要写库的两个点上各自调一个带 `@Transactional` 的小方法。

### 4.4 异步基础设施

```java
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean("visionExecutor")
    public TaskExecutor visionExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(1);       // SQLite 单写，必须串行
        executor.setMaxPoolSize(1);
        executor.setQueueCapacity(50);     // 排队而非拒绝
        executor.setThreadNamePrefix("vision-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }
}
```

**`CallerRunsPolicy` 的选择理由**：队列满时让提交者线程自己跑，而不是丢弃。图片解析丢一条用户是感知不到的（界面只显示「排队中」），静默丢弃是项目最忌讳的失效模式。

### 4.5 异步链路

```
POST /api/v1/inbox/{id}/parse
  → 校验：存在、origin=image、有附件、未在解析中
  → UPDATE parse_status='running'（短事务，立即提交）
  → ai_job INSERT (status='pending')，返回 jobId
  → 提交到 visionExecutor（立即返回，不阻塞 HTTP）

visionExecutor 线程：
  → 读附件（无事务）
  → 降采样（无事务）
  → 调视觉模型（无事务，耗时 3–10 秒）
  → 解析 JSON，落 ai_payload / ai_category / ai_confidence / status='processed'
    （短事务）
  → parse_status='success'；失败则 'failed' + error_msg
```

## 5. 视觉抽取设计

### 5.1 为什么不能走 OCR

用户给的两个例子恰好是 OCR 的天敌：

| 场景 | OCR 输出 | 丢失的关键信息 |
|---|---|---|
| 微信「我答应给谁什么数据」 | 左右两列气泡被拉平成一段 | **归属**：哪句是我说的。而「我答应」完全依赖归属 |
| 邮件截图 | 发件人/收件人/正文混成一坨 | **角色**：谁在要求、谁在承诺 |

信息藏在**版面结构**里。必须让模型看图，而不是看 OCR 结果，它需要理解「绿色气泡在右侧 = 我发的」这类版面语义。

### 5.2 降采样

原图 5 MB 直接送模型太浪费。服务端先缩到**长边 1600px**（保住气泡文字可读性），token 与延迟都显著下降。

**降采样与存档是两件事**：原图完整保留在 `attachments`，只有送模型的那份是缩小的。降采样用 `ImageIO` + `Graphics2D`，无需新依赖。

### 5.3 输出结构

```json
{
  "docType": "chat",
  "docConfidence": 0.86,
  "rawText": "老王：那个销售数据你什么时候给我\n我：明天下午发你",
  "participants": [
    { "name": "老王", "role": "counterparty" },
    { "name": "我",   "role": "self" }
  ],
  "items": [
    {
      "category": "task",
      "title": "给老王发销售数据",
      "due": "2026-09-16",
      "dueSource": "inferred",
      "dueHint": "明天下午",
      "priority": "P1",
      "counterparty": "老王",
      "quote": "我：明天下午发你",
      "confidence": 0.78
    }
  ]
}
```

**三个字段是设计决策，不是可选项**：

- **`quote`**：每条必须附回原图里对应的那句话。这是**用户唯一能快速核验的方式**——确认页把 `quote` 高亮，一眼看出模型有没有读错。没有 `quote` 的抽取结果只能盲信。
- **`dueSource`**：`extracted` / `inferred` / `missing`。截图里大部分时间是 `inferred`，必须标出来。
- **`confidence`**：条目级。低于阈值的默认不勾选。

### 5.4 Prompt 关键规则

写进 system prompt 的硬规则（每条都对应一个已知错误）：

1. **「有交付动作 + 有接收方」判为 task**，不要判成 knowledge。
   「我答应给老王发数据」有明确动作（发）和接收方（老王）→ task。
   判据是「**有没有一个需要被完成的状态**」。
2. **时间是相对表述时必须回算但标 `inferred`**。
   「明天下午」→ 结合截图状态栏日期回算，`dueSource: "inferred"`。
3. **图上没有时间就留空**，`due: null` + `dueSource: "missing"`。**不许猜**。
4. **气泡归属以版面位置判断**，右侧/绿色为 self，不要按文字内容猜。
5. **每条必须给 `quote`**，且 quote 必须是图上原文，不许改写。
6. **无关内容（表情包、广告、系统提示）不产出 item**。
7. **输出纯 JSON，不要 markdown 代码块包裹**（对齐既有 `LlmClassifyProvider.SYSTEM_PROMPT` 的做法）。

### 5.5 复用已有配置 + 新增视觉模型

现有配置（`SettingsService` L24-28）：

```java
KEY_AI_ENABLED   = "ai.enabled";
KEY_AI_BASE_URL  = "ai.base_url";
KEY_AI_MODEL     = "ai.model";
KEY_AI_API_KEY   = "ai.api_key";
```

只有**一个** `ai.model`，但同一 `base_url` 下文本模型与视觉模型通常不同名。所以 V10 新增 `ai.vision_model`。

**必须处理的降级**：用户配的模型可能不支持多模态。此时模型会返回错误而不是结果。
→ 解析失败时给明确文案：「当前配置的模型「xxx」不支持图片解析，请在设置页填写视觉模型」。
→ 不要笼统报「解析失败」——用户无法据此行动（对齐硬原则：报错要能指导操作）。

### 5.6 顺带提及：客户端重复问题

项目里已有**三份各自独立实现的 OpenAI 兼容客户端**：

| 类 | 用途 |
|---|---|
| `LlmClassifyProvider` | 收录整理 |
| `SearchExpandClient` | 搜索扩展 |
| `LlmAnswerClient` | 知识问答 |

三者都重复实现了：endpoint 拼接（`baseUrl.replaceAll("/+$","") + "/chat/completions"`）、`Authorization: Bearer` 头、超时配置。

再加 vision client 就是**第四份**。

→ 建议：先抽一个 `OpenAiCompatClient`（只做「发 messages 数组、收 content 字符串」），四个调用方各自负责构造 messages。**但这是重构，不该混在图片功能里做**——先按同样形态写第四个，重构单独排期。

## 6. 确认页交互（仅收录页）

### 6.1 布局

```
┌──────────────────────┬────────────────────────────────┐
│                      │ 识别为：微信聊天记录  ▾        │
│   ┌──────────────┐   │ 共 2 条，已勾选 1 条           │
│   │              │   │ ┌────────────────────────────┐ │
│   │    原图      │   │ │ ☑ 任务  给老王发销售数据   │ │
│   │  （可缩放）  │   │ │   对方：老王                │ │
│   │              │   │ │   截止：2026-09-16         │ │
│   │              │   │ │        ↑ 根据「明天下午」推算│ │
│   └──────────────┘   │ │   证据：「明天下午发你」    │ │
│                      │ └────────────────────────────┘ │
│   识别文字 ▾         │ ☐ 收藏  销售数据相关讨论       │
│   （可展开校对）     │   证据：「那个数据你看下」      │
│                      │                                │
│                      │ [ 忽略这张图 ]  [ 确认 1 条 ]  │
└──────────────────────┴────────────────────────────────┘
```

### 6.2 五条界面原则

**① 原图与结果并排，不折叠。** 用户核验方式是眼睛在图和结果间来回扫。图藏起来，核验成本大于自己重写。

**② 每个字段标来源。** 「识别」/「推算」不是装饰，是责任划分。

**③ 低置信度默认不勾选。**
- `≥ 0.80`：默认勾选
- `0.60 – 0.80`：默认**不**勾，高亮提示
- `< 0.60`：折叠进「另 N 条疑似内容」，默认收起

**默认全勾会让「确认」退化成「盲点确定」**；默认全不勾又显得没用。

**④ `rawText` 可展开校对。** 因为决策是落库、会被全局搜索命中，用户需要能看见到底存了什么。这是对「rawText 落库」这个决策的配套透明措施。

**⑤ 提供「忽略这张图」的明确出路。** 截图里常有大量无关信息。忽略后附件**仍保留在收集箱**，只是不生成实体。

### 6.3 识别失败的回退（不许静默）

视觉模型不可用（网络断、超时、配额满、模型不支持视觉）时：

- **不是报错弹窗**，而是降级：图作为普通附件收录，`status='pending'` + `parse_status='failed'`，`raw_content` 填「[图片]」
- 界面文案：「图片已收录，但没能读懂内容——可在整理页手动补充文字」
- 用户手动补文字后重新走既有分类链路

这对应既有的 failed 态设计：**收录页 = 收集箱 + 整理合并，`state.inbox` 要取 `pending + failed`**——失败的条目只有这一处会露出。

**绝对不能**：识别失败当没发生、静默丢弃。这是项目里最忌讳的失效模式。

## 7. 四个入口的差异化

### 7.1 收录页

- 图片区**常驻在输入行下方**（它没有折叠态，是单行 `.inbox-compose`）

### 7.2 任务 / 日程 / 收藏表单

三者共用 `.composer-body`，图片区统一放**最后一行**：

```html
<div class="c-row c-media-row">
  <span class="c-label">图片</span>
  <div class="media-strip" data-media-for="task"></div>
  <button class="media-type-button" type="button" data-media-add="task">＋</button>
```

| 表单 | 选图后行为 |
|---|---|
| 任务 | 上传完成后**立即解析**，异步回填 `#taskTitle` / `#taskDue` / `#taskPriority` |
| 日程 | 回填 `#eventTitle` / `#eventDate` / `#eventStart` / `#eventEnd` |

**回填规则（关键）**：

- 提供「撤销回填」按钮，一键恢复
- **解析不阻塞提交**：用户点「新建」时若解析未完成，正常提交（图作为附件），不强制等待

⚠️ **项目踩过的坑**：`.edit-panel` 是任务/日程/收藏三视图**共用类**。新增 `media-strip` 的 CSS 必须**带容器前缀限定**（`.composer-body .media-strip` / `.edit-panel .media-strip`），绝不能裸写 `.media-strip`——否则两个控件的选择器会互相串，且**控制台不报错**。

### 7.3 与「搜索行 / 新建行互斥」的关系

项目已定死：**同一行同一时刻只能有一个展开态**（放大镜展开则新建收起）。

图片区**不新增展开态**——它是新建表单的从属内容，随 `.composer-body` 一起显隐。不需要改动 `setSearchOpen()` 的既有逻辑。

## 8. 落盘与安全

### 8.1 目录结构

复用**已存在但一直没人用**的 `<data-dir>/attachments`（`WorkbenchDirectoryInitializer` 已 `Files.createDirectories`）：

```
<data-dir>/attachments/
  2026/09/
    a3f1b2c3d4e5f6a7.png     ← 落盘名 = sha256 前 16 位 + 白名单后缀
```

### 8.2 安全规则

- **落盘名不取用户原文件名** —— 最重要的一条。原文件名含 `/`、`..`、控制符，直接拼路径就是目录穿越。落盘名由 sha256 生成，天然安全。
- **二次校验**：解析后的绝对路径必须 `startsWith(attachmentsRoot)`，对齐 `ObsidianVaultService.resolveInsideVault` 的做法。
- **`original_name` 只存库、只用于展示和报错，永不参与路径拼接。**
- **类型白名单**：`image/jpeg`、`image/png`、`image/gif`、`image/webp`。用 MIME + **文件头魔数双重校验**（后缀可伪造）。
- **大小上限 5 MB / 张，9 张 / 条**。

### 8.3 Spring 配置（当前完全没有）

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 5MB
      max-request-size: 6MB
```

⚠️ 超过 `max-file-size` 时 Spring 抛 `MaxUploadSizeExceededException`，**默认返回 500**。必须在 `@RestControllerAdvice` 里拦成 400 + 中文提示（硬原则：非法输入不许落 500）。

### 8.4 读取接口

```
GET /api/v1/attachments/{id}/raw
→ Content-Type: image/png
  Cache-Control: private, max-age=31536000, immutable
  ETag: "a3f1b2c3d4e5f6a7"
```

- 落盘名含 sha256，内容不变则 URL 不变，`immutable` 长缓存安全
- **必须流式写，不能 `byte[]`** —— 5 MB × 9 张 = 45 MB 进堆
- 走登录拦截（`/api/v1/**` 已被 `WebMvcConfig` 覆盖），**不做公开静态映射**（裸静态目录会绕过鉴权）

## 9. 隐私（决策为「外部模型 + rawText 落库」，本节是配套措施）

用户已选外部模型 + rawText 落库。这不改变，但**必须配套三件事**，否则是悄悄发生的风险：

### 9.1 发送前的明确告知

首次使用图片解析时一次性提示，此后每张图在缩略图上带一个不可忽略的标记：

> 图片内容将发送至外部模型服务进行识别。聊天记录、邮件截图可能包含他人个人信息。

**理由**：技术上能做 ≠ 默认应该做。用户需要知道第三方内容正在离开本机。

### 9.2 全局搜索必须能区分来源

`rawText` 落库后，**全局搜索会搜出聊天记录原文**。这是决策的直接后果，需要配套：

- 搜索结果中图片来源的条目显示「来自图片解析」标签
- 提供「搜索时排除图片解析内容」的筛选开关
- 涉及的红线：**不调 `refreshAll`**、走 `openSearchResult(item)` 统一分发

### 9.3 提供「仅本地」开关

设置页提供 `ai.vision_local_only` 开关，开启后：
- 图片**只作附件**，不做视觉解析（不发送任何内容到外部）
- 界面明确显示「本地模式：图片不会被解析」

这是给敏感截图的逃生通道，实现成本极低（一个 if 判断），但对「我有一张不想外发的图」这个真实场景是唯一的解。

## 10. 错误码与文案

| 场景 | HTTP | 码 | 文案 |
|---|---|---|---|
| 非图片类型 | 400 | `ATTACHMENT_INVALID` | 「xx.pdf」不是图片格式，支持 jpg/png/gif/webp |
| 超过 5 MB | 400 | `ATTACHMENT_INVALID` | 「xx.png」3.2 MB 超过 5 MB 上限 |
| 空文件 | 400 | `ATTACHMENT_INVALID` | 「xx.png」是空文件 |
| 超过 9 张 | 400 | `ATTACHMENT_INVALID` | 最多 9 张图片 |
| 附件不存在 | 400 | `ATTACHMENT_INVALID` | 附件 12 不存在或已被删除 |
| 附件已占用 | 400 | `ATTACHMENT_INVALID` | 附件 12 已挂在其他记录上 |
| **模型不支持视觉** | 400 | `VISION_UNSUPPORTED` | 当前配置的模型「xxx」不支持图片解析，请在设置页填写视觉模型 |
| 视觉服务超时 | 400 | `VISION_FAILED` | 图片识别超时，可稍后重试或在整理页手动补充 |
| AI 未启用 | 400 | `AI_DISABLED` | AI 整理未启用，图片已作为附件保存 |
| 解析中重复触发 | 409 | `RESOURCE_CONFLICT` | 这张图正在解析中 |
| 上传超限（Spring） | 400 | `ATTACHMENT_INVALID` | 文件超过 5 MB 上限（**不许落 500**） |

**同一约束在不同入口必须用同一个码**：四类实体的图片非法全部走 `ATTACHMENT_INVALID`。

## 13. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 视觉模型读错日期/归属 | 产生错误实体 | 确认页 + `dueSource` 标记 + quote 高亮 + 低置信度不勾选 |
| 外部模型发送他人信息 | 隐私 | 发送前告知 + 仅本地开关 + 搜索来源标签 |
| `rawText` 落库污染全局搜索 | 搜索结果混入聊天记录 | 来源标签 + 可排除筛选 |
| 单线程串行导致排队 | 一次传 9 张要等很久 | 队列 50 + CallerRunsPolicy 不丢弃；界面显示排队位次 |
| `SQLITE_BUSY` | 写入失败 | 事务边界切碎（4.3）+ busy_timeout 兜底 + 单线程 |
| 第四个重复客户端 | 维护成本 | 记录在案，重构单独排期 |
| Vault 图片膨胀 | Obsidian 同步压力 | 原图不写 Vault，**只写降采样后的版本** |

### 一个尚未决策的点

**知识类图片要不要压缩后写进 Vault？**

若 `knowledge` 落点把原图写进 Vault：5 MB × 9 张 × 每天 → Vault 快速膨胀，且 Obsidian 同步可能吃不消。

建议：**Vault 只写降采样版本**（长边 1600px，约 200–400 KB），原图留在 `attachments`。这样 Obsidian 里能看，库不爆炸。

此点需确认后落地。

### 孤儿附件清理

用户在表单里传了图然后关掉页面 → `owner_id IS NULL`。

→ 新增 `AttachmentCleanupScheduler`（参照 `DailyBackupScheduler` 的 `@Scheduled` 形态），**每日清理超过 24 小时仍未绑定的附件**（物理删除，同时删磁盘文件）。

否则 `attachments` 目录会变成无声的垃圾场。

## 14. 顺带发现（与本次需求无关，但值得记录）

`application.yml` 的 `dev` profile 把 `server.address` 设为 `0.0.0.0`：

```yaml
spring:
  config:
    activate:
      on-profile: dev
server:
  address: 0.0.0.0
```

而 `/api/v1/collect/agent` 是**免登录**接口，其安全性完全依赖「端口只绑 127.0.0.1」（见 `WebMvcConfig` 注释）。

→ **用 dev profile 启动时，免登录接口会暴露到局域网。** 若将来改动绑定，必须先给该接口加鉴权。

这不是图片功能的问题，但既然看到了就记一笔。

## 15. 实现差异清单（设计 vs 落地，2026-09-16）

设计期的推演与最终实现有若干差异。**以下以代码为准**；正文（§1–§14）保留当时的推理过程，
不逐条回改，避免把「为什么这么想」的线索抹掉。

### 15.1 接口：实际路径与设计不同

| 设计稿写的 | 实际实现 | 说明 |
|---|---|---|
| `POST /inbox/{id}/parse` | `POST /api/v1/inbox/parse-images` | 改成**按附件 id** 触发，一次可多张；`/{id}/parse` 那种「按收录条目」的路径不成立——解析发生在条目存在之前 |
| `POST /{id}/confirm-items` | `POST /api/v1/inbox/confirm-items` | 同上，与收录 id 无关，body 里带 `items[{inboxId, confirm}]` |
| （无） | `GET /api/v1/inbox/parse-status` | 设计漏了轮询接口，实际必需 |

`parse-images` **同步返回 202 之前会先做完整校验**（本地开关 / 是否配置视觉模型 /
附件是否存在且是图片 / 列表非空）。理由：这类失败本来就能提前知道，放进异步任务里
只会落进日志，用户点完「解析」看到一片安静。

### 15.2 四入口**不是**「同构 + 差异」，而是两种形态

设计 §7 说「收录页走确认页，三个表单走预填」，方向对；实现时把它固化成了两条**独立链路**：

| | 收录页 | 任务 / 日程 / 收藏表单 |
|---|---|---|
| 图片去向 | 交给视觉模型解析 | 同左 |
| 解析结果 | 生成 N 条 `status='processed'` 的待确认条目 | **不生成任何记录**，只回填表单字段 |
| 触发 | 点「收录」 | 点「识别填表」（新增按钮） |
| 用户动作 | 逐条核对 → 「确认生成」 | 核对表单 → 点「保存」 |

表单页**没有**确认页：用户本来就在填表单，预填后他还能顺手改；硬塞一个确认页会把
「补张截图」变成两段流程。

### 15.3 前端控件：从「双按钮」收敛到「一个加号」

设计的想象是「两个上传框」。用户看过静态稿后否掉了，最终形态：

- 左下角一个 **`＋AI`** 圆形按钮 → 选图 / 拖入 / 粘贴，三种路径都进「解析图片」
- 「附件」是**独立的小按钮**，放在提交按钮左边，显示 `附件 3` 计数
- 拖拽时**按文件类型自动分流**：图片进解析、其它进附件，用户不用先记该点哪个
- 整个输入容器是拖拽落点

### 15.4 落库形态：占位条目**复用**而非新建

设计没写这条，实现时必须处理：解析要 3–10 秒，期间界面上得有个东西表示「正在干活」。

做法是先插一条 `status='pending'` + `parse_status='running'` 的**占位条目**，解析成功后
用 `updateParsedFromImage` 把它**改写成第一条结果**，其余 N-1 条另建。

不复用的话，页面上会多出一个「正在解析…」的死块——它不属于
pending / processed / archived 任何一种状态，**没有任何入口能删掉它**。

`raw_content` 的分配也有讲究：**第一条用整图原文**（用户核对的底稿），
**其余条用本条的 `evidence` 片段**。全部塞整图原文的话，整理页会出现 N 个
一模一样的长文本块，用户分不清哪条是哪条。

### 15.5 事务边界：新增 `InboxParseWriter` 门面

设计的 §4.3 说了「调模型不能持有事务」，实现时发现还有个**循环依赖**：
`InboxService` 需要注入 `VisionParseService`，而 `VisionParseService` 又要写 `inbox_item`。

→ 新建 `InboxParseWriter`：只有 `begin / fail / finish / log` 四个方法，
全部 `REQUIRES_NEW` 短事务。它既打断了环，也从类型上钉住「解析写库只允许做这几件事」
（这个类里没有 `confirm` / `classify` / `delete`）。

跨包访问也一并解决了：`AttachmentRecord` / `InboxRecord` 是包级可见的，
与其提升为 `public`（等于把整表形态暴露出去），不如给只读快照
（`AttachmentService.ImageSource`）。

### 15.6 顺带修掉的三个真实缺陷

| 缺陷 | 症状 | 修法 |
|---|---|---|
| `InboxService.confirm()` 标题兜底用 `record.raw` | 标题上限是 200，却可能写出 4000 字标题，之后编辑保存被 `@Size(max=200)` 拒掉 | `TextUtil.clip(..., MAX_TITLE_LENGTH)` |
| `InboxRepository.markParseFailed()` 传了 4 个参数给 3 个占位符 | 驱动把 id 顶掉，「更新了 0 行」而**不报错**，解析失败后条目的 failed 状态永远写不进去 | 删掉多余的 `now` |
| `renderParseStatus()` 缺 0/0 早返回 + 整体赋 `className` | 首页 `running=0 && failed=0` 时，进度条**照样显示**，且文案是自相矛盾的「有 **0** 张图片没能解析」 | 补 `if(running<=0&&failed<=0){…hidden…return}`，并让分支渲染不再整体覆盖 `hidden` 类 |

前两个是**后端测试**抓出来的（`VisionFlowTest`）；第三个是**真页面冒烟**
（`output/smoke-media/shot_media.js`）抓出来的 —— 它纯属前端渲染逻辑，
单元测试与 MockMvc 都覆盖不到，只有真浏览器 + 真 CSS 才能暴露。
这条同时暴露了 `.media-cnt[hidden]`（属性选择器）与 JS 的 `classList` 机制不匹配、
靠全局 `.hidden{display:none!important}` 兜底才「看起来正常」的死代码，已一并清除。

### 15.6.1 迁移文件的 Flyway 校验失败（环境问题，非代码缺陷）

落地过程中 `V10__attachment.sql` 在**已被 apply 之后又追加了两列**
（`raw_truncated` / `source_attachment_id`），导致 Flyway 8.5.13 启动时
`Migration checksum mismatch for migration version 10`，容器进入**崩溃重启循环**
（`ps` 里显示的 `Up N seconds (health: starting)` 是重启后重新计时，不是"启动慢"）。

**关键点**：这里**不能**用 `flyway repair` —— repair 只对齐 checksum，Flyway 于是认为
V10 已完成、**跳过**缺失的两个 `ALTER TABLE`，结果服务能启动但一碰新列就 `no such column`，
比启动失败更难查。正确顺序是：① 只读查库确认缺哪些列 → ② 手工 `ALTER TABLE` 补齐
→ ③ 把 `flyway_schema_history` 里 V10 的 checksum 改成 Flyway 日志中
`Resolved locally` 给出的权威值 → ④ 重启。

**教训**：迁移文件一旦 apply 过就当**只读**，要补列请新开 `V{n+1}`。
排查与修复的完整脚本见技能 `personal-workbench-dev-ops` §6.2。

### 15.7 实际测试覆盖

| 测试类 | 用例数 | 覆盖 |
|---|---|---|
| `VisionFlowTest` | 10 | 降采样（等比 / 不放大 / 非图片返回 null）、配置闸门（未配 / 缺视觉模型名 / 空列表）、仅本地开关、非图片附件、落库形态四种 |
| `SchemaMigrationTest` | +2 | 存量收录不变成图片条目；半绑定附件被 CHECK 拦下 |
| `InboxFlowTest` | +9 | 图片条目**永不参与**批量确认（含 0.95 高置信度）、人工确认仍可用、纯文本不受影响、批量确认整体回滚 / 条数 / 上限 50、解析进度统计、未配置时报 3015 |
| `shot_media.js`（真页面冒烟） | 17 条断言 + 6 条变异 | 四入口图片区结构、`＋AI` 展开后可见、三个「识别填表」且收录页没有、进度条常态不显示、拖拽分流、计数徽标、上传/移除清理 |

**在途变异已验证**：
- 后端：注释掉 `if ("image".equals(record.origin)) continue;`，
  `imageItemsNeverJoinHighConfidenceBatchEvenWhenConfident` 立刻转红
  （`$.data.length()` expected `<0>` but was `<1>`）。
- 前端：删掉 `renderParseStatus()` 的 0/0 早返回，「无解析任务时进度条不显示」转红 ——
  即 15.6 表格里第三个缺陷的**回放**，证明该断言有约束力。
  冒烟脚本 6 条变异全被抓住、假绿 0。

**没能真验证的部分**：视觉模型不能真调（不能联网、不能把用户数据发出去），
所以 `VisionProvider` 的网络链路由「配置闸门 + 请求体构造」间接覆盖，
真实响应解析未测。这是已知的验证缺口。

另外，两个新接口在**真实容器**里已确认注册（`GET /api/v1/inbox/parse-status`、
`POST /api/v1/inbox/parse-images` 均返回 401 `code 2002`「请先登录」——
是"路由存在但被鉴权拦住"，不是 404）。未登录状态下的 3015 / 1002 等业务码
由 MockMvc 覆盖，未在真实容器复测。
