# 日程页周视图设计

> 2026-09-13 定稿并实现。本文记录**为什么是现在这个形态**，以及实现时不能碰的几条线。
> 需求原话：「日程按周为维度展示，每个周都可以折叠和展开。每个周都是七行，从周一到周天。
> 每个日程记录就是这行中的一个卡片，按时间顺序从左往右排序。注意美观，参考成熟美观的
> SaaS 项目、日程管理系统。」

## 1. 需求对齐过程（四轮，中间纠正过一次方向）

样式不是一次说清的。记下来，免得日后又按错的那一版改：

| 轮次 | 用户表述 | 落到的结论 |
|---|---|---|
| 1 | 按周展示、每周可折叠、七行、卡片按时间从左往右 | 提出两个方案（等宽卡片流水 / 比例时间轴），见 §2 |
| 2 | 四问四答 | 选定等宽卡片流水；**直接替换**按日视图；无时间日程沉行首；上/下箭头 + 回到本周 |
| 3 | **纠正**：「第一条展示下一周（默认折叠），第二条展开当前周，第三条展开上一周」 | 纵向顺序 = **下一周 / 本周 / 上一周**（未来在上、过去在下） |
| 4 | 「去掉『日程 本周：xxx』这条信息，三个按钮放在当前周卡片右上角」 | 没有独立顶栏；「回到本周 / ↑ / ↓」挂在本周那一条的周头右端 |

**教训**：用户用方位词（「第一条」「上面」「前面」）描述布局时，**先画图对齐再动手**。
第 3 轮之前我理解成「第一条是本周」，差一步就做出一个完全反过来的页面。

## 2. 为什么是「等宽卡片流水」，不是「比例时间轴」

「成熟 SaaS 的日程系统」里，周视图通常有两种做法。我们选了看起来更朴素的那个，理由是**测量结果**：

七行布局下，每行的可用宽度 = 1040px 内容区 − 84px 日期列 − 内边距 ≈ **570px**。
按 08:00–22:00 共 14 小时折算：

| 日程时长 | 比例时间轴里的卡片宽度 | 后果 |
|---|---|---|
| 30 分钟 | ≈ 20px | **标题一个字都放不下**，退化成一条没有文字的色条 |
| 1 小时 | ≈ 40px | 只够显示「11:00」 |
| 3 小时 | ≈ 122px | 勉强可读 |

而「站会 / 快速同步 / 对齐」这类 30–60 分钟的短日程恰恰是日常主力。卡片变成色条之后，
用户得逐条点开才知道那是什么 —— **比不显示更糟**。

第二条理由更硬：`EventService.findConflicts()` 的设计是「时间重叠**只提醒、不阻止保存**」，
即重叠数据真实存在。比例视图里重叠卡片必然互相遮挡，而**「遮挡」在本项目里属于
「控制台不报、渲染脚本也查不出、只有截图能发现」的静默失效**（任务泳道的
`.lane{overflow}` 那条禁令就是为它立的）。不能主动把这个坑引到日程页。

代价：**看不出时间间隔的比例**（10:00 与 15:00 之间不会真的空出 5 小时）。
顺序语义改由另外两件事承担，两者缺一不可：

1. 行内卡片**严格按 `start_time` 升序**从左往右；
2. 每张卡片自带**时间徽标**（`09:00 – 09:30`）。

## 3. 最终形态

```
┌ 2026年9月14日 – 9月20日  下一周              3 项日程 · 点这一行展开 ┐  ← 默认折叠
├ 2026年9月7日 – 9月13日  [本周]   第 37 周 · 12 项   [回到本周][↑][↓] ┤  ← 默认展开
│ 周一 09.07 │ [09:00 站会][11:00 产品评审][14:00 需求梳理][16:30 客户对齐]
│ 周二 09.08 │ [10:00 项目周会]
│ 周三 09.09 │ [未排时段 整理资料][09:30 设计走查][15:00 方案评审]
│ 周四 09.10 │ 这一天还没有日程
│ 周五 09.11 │ [09:00 站会][10:30 复盘]
│ 周六 09.12 │ [11:00 家庭采买][15:00 陪孩子]     ← 今天，整行淡蓝
│ 周日 09.13 │ 这一天还没有日程
└ 2026年8月31日 – 9月6日  上一周               4 项日程 · 点这一行展开 ┘  ← 默认折叠
```

- **三条固定**，顺序「下一周 / 本周 / 上一周」，本周永远居中。
- **手风琴：任何时刻只有一个周展开**（2026-09-13 用户第二次明确）。
  点任意周头 → 它成为唯一展开的那一条，其余自动收起。点**已展开**的那条是幂等的（不收起）——
  「永远有一个展开」才能让「我现在在看哪一周」始终有明确答案。
- **七行是写死的七天**（`[0,1,2,3,4,5,6].map`），不跟着数据长度走 —— 没日程的那天也要在，
  否则「七行」就成了「有日程的那几天」，用户会以为周日不存在。
- 卡片**等宽 136px**（一行放四张）、两行内容（时间 + 标题）、左侧 3px 色条表达类型：
  会议 = 绿 / 深度块 = 蓝 / 其他 = 灰。
- **今天那一行**整行淡蓝 + 左侧日期格高亮。
- **「回到本周 / ↑ / ↓」挂在那条正在展开的周上**（2026-09-13 第二次修正：不是固定挂本周）。
  切周时这三个按钮必须**搬 DOM 节点**过去 —— 只切 class 的话它们会留在原来那一周，
  用户看到的是「切过去之后按钮不见了」。
  - ↑ = 往列表上方要更远的一周（未来方向）；↓ = 往列表下方要更早的一周。
  - 目标周**已经在列表里**时不再重复追加，但仍然会展开它并滚过去（否则就是「按了没反应」）。
  - 追加/切换完**必须滚过去**，否则用户看不到任何变化。
  - 「回到本周」= 复位成默认三条 + 展开本周 + 滚回本周，任何时候都可点（不做禁用态：
    它包含「滚回本周」这个作用，置灰会让只想滚回去的用户以为按钮坏了）。
- 卡片区**横向滚动、绝不换行**（换行就不是「七行」了）。

## 4. 没有开始时间的日程

`schedule_event.start_time` **允许为空**（`V1` 迁移起就是这么定的），后端排序里专门有一段
`CASE WHEN start_time IS NULL THEN 1 ELSE 0 END`。也就是说库里真的存在「只有日期和标题、
没有具体时段」的日程。

**处理：沉到该行最左侧，虚线框 + 「未排时段」徽标，并且计入行内条数。**
不给它位置就等于静默丢掉一条真实数据。`eventsOfDay()` 里显式分桶 —— 后端把它排在最后，
前端不能直接用返回顺序。

## 5. 展开 / 收起的四处硬要求

1. **收起靠 CSS**（`.week-block.collapsed .week-body{display:none}`），DOM 保持完整。
   所以切换只动 class、**不重绘**，也就不会把滚动位置弹回顶部。
2. **「当前展开的是哪一周」存在 `state.expandedWeek`**，不能只挂 DOM class：
   `refreshAll` 每次都会重建周条，只挂 DOM 的话下一次刷新就自己弹开了（时间线折叠踩过同一个坑）。
   存「哪个展开」而不是「哪些收起」——后者能表达出「全展开 / 全收起」，
   而在手风琴下这两个状态**都不该存在**。
3. **切换时按钮要跟着搬**：`.wh-actions` 节点 `appendChild` 到新的周头右端。
   只切 class 的话按钮留在原来那一周，表现是「切过去之后按钮不见了」。
4. **收起的周条必须写出条数**（「N 项日程 · 点这一行展开」）。只剩一个光秃秃的日期区间，
   用户会以为那一周是空的 —— 「看不出来」在本项目里等同于「功能坏了」。

## 6. 后端接口变更

`GET /api/v1/events` 现在是**三种形态共用一个入口**（与 `tasks` / `memos` 同构），
优先级自上而下：

| 参数 | 形态 | 说明 |
|---|---|---|
| `q` | 全文检索 | 命中**全部日期**（含待定区），忽略 `date` / `from` / `to` |
| `from` + `to` | 区间查询 | 周视图一次取回所有可见周，**两者必须成对** |
| `date` / 缺省 | 单日 | 省略或空串 = 今天 |

- 新增 `EventRepository.findByRange(from,to)`，SQL 里用显式 `event_date IS NOT NULL`
  把待定日程挡在外面 —— 不依赖「`BETWEEN` 遇到 NULL 判非真」这种巧合。
- `from` / `to` 只给一个时**报错**（1002 + 「同时提供 from 与 to，例如 …」），
  不做「另一半默认等于自己」的隐式兜底：那样用户少打一个参数会拿到一个看起来正常、
  实际不是他要的区间，界面上没有任何迹象。
- 首尾两天都含在内（闭区间）：少一天就意味着那一行永远是空的。
- **为什么必须加这个接口**：不加就只能按天循环调 7 次，一次页面刷新会从 11 个请求涨到 17 个，
  与「判据只有一个：数真实请求」的约定直接冲突。

前端 `WorkbenchApi.events` 相应从 `(date, q)` 两个位置参数收成 `params` 对象
（形态从两种变成三种之后，位置参数反而更难读：`events(null,"客户")` 是什么意思？）。

## 7. 移除按日视图后的三处连带改动

`state.viewDate`、`.day-nav`（前一天 / 后一天 / 日期选择器 / 回到今天）、`dayLabel()` 一并移除。
**下面三处不改，就会出现「点了没反应」或「刚建的东西看不到」**：

| 位置 | 改法 |
|---|---|
| 驾驶舱下钻 `drillEvent` | 先把该日期所在的那一周 `ensureWeek()` 放进可见列表 → `loadEvents()` → `scrollToWeek()` → 高亮。顺序不能反 |
| 全局搜索落点 `openSearchResult`（schedule 分支） | 同上 |
| 新建日程的默认日期 | 改为**默认今天**，并在 `createEvent` 里判断 `isDateVisible(date)`：不在当前显示的周里就提示「可用周头右上角的 ↑ / ↓ 翻到那一周」 |

另外两条保持不变：

- **检索态仍走平铺列表**（`#eventResults`），不套周网格 —— 命中跨月时会散成十几个
  只有一条卡的周条，反而看不出结果。
- **「待定时间」区原样保留**：它管的是「不知道哪一天」，与「有日期但没具体时段」是两回事。

**过程中被测试抓到的两个真问题**（都不是靠肉眼发现的）：

1. **默认三条全部展开了**。`syncVisibleWeeks` 只设了 `visibleWeeks` 没设 `collapsedWeeks`，
   而静态断言当时用的夹具自己拼了一套周列表，把产品的缺失**掩盖**住了 ——
   「夹具自己造一份状态」等于把被测规则抄了一遍。改成夹具直接调 `syncVisibleWeeks()` 后才暴露。
2. **`state` 定义里那三个周视图字段丢了**（`weekBase` / `visibleWeeks` / `collapsedWeeks`）。
   同样是夹具补了字段 => 渲染断言全绿，只有那条「折叠状态必须存在 state 里」的静态断言抓到了它。

> 两条的共同教训：**夹具越是「体贴地补齐」，越容易把产品的缺陷盖住。**
> 夹具应当尽量调用产品的真实函数，而不是替换它。

## 9. 重复日程：「每周 X」（2026-09-13 追加）

需求原话：「如果我收录最终进入日程的信息是每周几做什么，你需要在连续 4 周的日程中都展示该记录」。

### 9.1 关键决策：物化成 4 条独立记录

用户在三个选项里选了「**要能只改某一次**」，这一条直接决定了实现方式：

| 方案 | 「只改某一次」 | 查询层 | 结论 |
|---|---|---|---|
| 一条记录 + 查询时展开 | 要额外存「哪一期被单独改过」的例外，再把主线与例外合并 | 每个读路径都要改（周视图 / 驾驶舱计数 / 冲突检测 / 检索） | ✗ |
| **物化 N 条 + 分组标记** | **天然成立**（改的就是那一条） | **零改动** | ✓ |

代价是「改标题要改 4 遍」—— 但用户要的正是「每一期独立」，所以这不是代价，而是预期行为。

### 9.2 数据与识别

- `V8__event_repeat.sql`：加 `repeat_group`（组标识 = **首期的 id**，不重复为 NULL）
  与 `repeat_total`（共几期，默认 1）。只加列，不重建表。
- 识别规则：`每` + `周X / 星期X / 礼拜X` → 4 期。**只做这一种** ——
  「双周」「每月 1 号」「每周一三五」都不识别，因为**误判出来的重复日程比不做更烦人**：
  用户得先意识到那几期是多余的，再手动删掉。
- `applyRepeatHint(raw, suggestion)` 是**独立于 provider 的一层后处理**：
  没配 AI 走本地规则、配了 AI 走 LLM，两条路径都要过它。
  否则「配了 AI 之后重复识别凭空消失」—— 而这种差异在界面上完全看不出来。
- 物化逻辑只有一处：`EventRepository.insertRepeating(...)`。
  手工新建与收录确认是两条写入路径，各写一份循环迟早会漂，而漂了之后
  表现是「收录进来的重复日程只生成一期」这种只在某一个入口出现的怪事。

### 9.3 边界

- **待定日程（没日期）一律不重复**：没有日期就谈不上「每周的同一天」，硬展开只能编一个日期出来。
- **组标识取首期的 id**：插入前拿不到，所以插完回填，后续各期直接带上它。
- **只按首期做一次冲突检测**：同一组各期是同一时刻的同一件事，逐期检测只会把同一条警告重复 N 遍。
- **时间线只写一条**，并注明「（每周，共 4 期）」—— 用户做的是「一件事」，不该在流水里留四条。

### 9.4 界面

- 卡片上只有两个字「**每周**」（136px 的卡片塞不下第二行解释），完整说明（共几期、能否单独改）
  挂在 `title` 上。时间行改成两端对齐，否则各卡片时间串长短不一，徽标位置会参差不齐。
- 编辑面板写明「**改这里只影响这一期**」—— 这就是选物化方案的全部理由；不说的话用户会不敢改。
- 「加入日程」表单有「每周 · 连续 4 周」选项，且**用完必须复位成「不重复」**，
  否则下一条日程会被静默生成 4 期。
- 收录确认卡提示「将一次生成 4 期」。
