## 0. 三十秒理解这个项目

**一句话**：给一位每天要处理大量碎片事务的程序员，做一个**装在自己电脑上、不用联网、解压即用的个人工作台**——脑子里冒出来的事 5 秒记下来，系统帮你分好类，每天早上打开就知道今天先干什么。

**它不是一个待办清单 App。** 市面上待办工具失败的原因不是功能不够，而是**录入太慢**：打开 App、选清单、填标题、设日期、选优先级——五步之后，那件事已经忘了。本产品的全部设计都围绕一个目标：

> **把「记录一件事」的摩擦降到接近零，把「决定今天先做什么」的成本降到零。**

**三条不可妥协的产品原则**（后面所有取舍都是它的推论）：

| 原则 | 含义 | 违反的代价 |
|---|---|---|
| **P1 零摩擦录入** | 一句话、一个回车、进收集箱。不要求当场分类、定优先级、选日期 | 用户不用了，因为记一条太麻烦 |
| **P2 每天 15 分钟清空** | 收集箱必须能快速清空，而不是越积越多 | 收集箱变成第二个垃圾桶 |
| **P3 本地优先、可复制** | 一台没装任何开发环境的 Windows 电脑，解压即用；数据只在本机 | 无法交付给同事，产品失去传播价值 |

## 1. 为什么要做：问题从哪来

### 1.1 用户画像

主角是一位 **Tech Lead / 后端架构师**（也是本项目的发起者），日常工作形态：

- 同时推进多个技术项目（限流方案、MR 评审、团队 1on1、跨部门对齐）
- 每天被打断 20+ 次：会议间隙、微信消息、临时插单
- 手头同时有工作事项（方案、评审、值班）和生活事项（家庭采购、班车时刻、报销）
- 已有 Obsidian 做知识沉淀，但**知识库不管待办**

### 1.2 四个真实痛点

| # | 痛点 | 具体表现 | 本产品的对策 |
|---|---|---|---|
| 1 | **想记的时候记不下来** | 微信里收到"帮我看下这个方案"，等有空打开待办 App 时已经忘了 | 收集箱：一句话回车即入库，不做任何分类要求 |
| 2 | **记下来了但沉底** | Notion / 备忘录里堆了 300 条，从不回看 | 每天固定整理 + 驾驶舱只推 Top3 |
| 3 | **速查信息无处安放** | 班车时刻、VPN 地址、奶粉型号散落在微信收藏、便签、截图里 | 备忘页签：工作/生活分组 + 全文检索 + 置顶 |
| 4 | **现有工具太重** | 待办 App 要么要联网同步（隐私顾虑）、要么要装一堆东西 | 纯本地单文件数据库，双击即用 |

### 1.3 为什么不用现成工具

| 工具 | 不用的原因 |
|---|---|
| Notion / 飞书文档 | 录入路径长（打开→找页面→新建→填字段），且核心是文档不是待办流转 |
| Things / Todoist / 滴答清单 | 每记一条都要决定清单、日期、优先级，违反 P1 |
| 手机自带备忘录 | 无状态流转、无逾期追踪、无每日聚焦 |
| Obsidian + 插件 | 知识管理很强，但待办流转和"今天干什么"需要大量插件拼装，且移动端体验弱 |

**结论**：这个产品的差异化不在功能多，而在**录入摩擦低 + 每天自动收敛**。任何增加录入步骤的需求都应该被质疑。

## 2. 产品形态：交付什么

### 2.1 版本 A / 版本 B 的边界

| | 版本 A（**本次交付**） | 版本 B（后续，不在本次范围） |
|---|---|---|
| 形态 | Windows 免安装 ZIP，自带 JRE 8 | Docker Compose |
| 使用者 | **普通同事**（非技术背景） | 技术同事 / NAS 用户 |
| 前置条件 | 无 | 需已安装 Docker Desktop |
| 访问方式 | 仅本机 `http://localhost:18080` | 可局域网 / 手机访问 |
| 包体 | ZIP ≈ 70 MB | 镜像 |
| 企业微信 / 语音 / 远程 | **不提供** | 提供 |

> **本文件的所有"产品定义"均指版本 A。** 需要企业微信或手机访问的场景，明确告知用户走版本 B，不要在版本 A 里做半成品。

### 2.2 同事视角的完整体验

```text
1. 拿到 personal-workbench-v1.0.0-win.zip（微信直接发，70MB）
        ↓
2. 解压到 D:\个人工作台（注意：不能放桌面/OneDrive，原因见 §9.3）
        ↓
3. 双击「启动工作台.cmd」
   ├─ 自动检查端口占用 / 数据目录权限 / 防止重复启动
   ├─ 首次自动建库（Flyway），用户无感
   └─ 健康检查通过后自动打开浏览器
        ↓
4. 首次配置向导（3 个必填：用户名、密码、时区）
   └─ AI / Obsidian 全部可选，可"稍后设置"
        ↓
5. 进入驾驶舱，已有 4 条示例数据，可以直接上手
```

**同事永远不需要知道**：Java、Spring Boot、SQLite、Flyway、Maven、Node、Docker。这些词不应出现在交付包的用户可见文本里。

### 2.3 产品定义（一句话）

> **一个纯本地、单用户、无需网络的个人工作台。**

拆成三条约束，任何需求与它冲突时以它为准：

1. **纯本地** — 不依赖任何公网服务；AI 是可选增强，关掉后核心功能 100% 可用
2. **单用户** — 无多账号、无协作、无权限体系；登录口令只防家人误触
3. **无需网络** — 断网状态下除了 AI 整理，所有功能正常

## 4. 统一语言（命名与文案必须按这个来）

**这是最重要的一节。** 代码里的类名、字段名、API 路径、界面文案，都必须使用下表右侧的词汇。混用同义词（如"笔记"和"备忘"）会导致 AI 生成出两套概念。

| 统一词汇 | 含义 | ❌ 禁止使用的同义词 |
|---|---|---|
| **收集箱条目**（inbox_item） | 用户随口记下的一句原始话，未经整理 | 速记、闪念、笔记、草稿 |
| **整理**（classify） | 把收集箱条目判定为任务/日程/备忘/知识四类的动作 | 分类、打标、解析、识别 |
| **确认**（confirm） | 用户认可整理结果，生成正式实体 | 提交、应用、采纳 |
| **任务**（task） | 需要完成、有状态和截止时间的事 | 待办、todo、事项 |
| **日程**（schedule_event） | 占据某个时间段的安排 | 日历、事件、会议、安排 |
| **备忘**（memo） | 需要反复查阅的静态信息 | 笔记、速查、收藏、便签 |
| **知识笔记**（knowledge_note） | 同步到 Obsidian 的内容（版本 A 隐藏） | 文档、文章 |
| **番茄**（pomodoro） | 一个 25 分钟专注周期的记录 | 专注、计时 |
| **时间线**（timeline） | 按时间倒序的操作流水 | 日志、动态、历史 |
| **驾驶舱**（dashboard） | 首页，回答"今天干什么" | 今日、首页、概览 |
| **今日主题**（theme） | ~~当天最重要的一件事，显示在驾驶舱顶部~~ **2026-09-20 已下线**（用户反馈没什么用）：卡片、`POST /api/v1/dashboard/theme` 与 `DailyPlanRepository` 一并移除；`daily_plan.theme` 列保留（该表仍被 `daily_plan_item` 外键依赖），只是不再有写入方 | 目标、焦点 |
| **顺延**（postpone） | 把逾期任务推到明天，并累计次数 | 推迟、改期、延后 |
| **空间**（group） | 备忘的工作/生活二分组 | 分组（在代码里可叫 group，界面叫"空间"） |

**界面文案风格**：简短、口语、不用感叹号、不用"亲爱的/太棒了"等营销腔。例如完成任务后的提示是「漂亮，这事终于落地了」这种克制的正向反馈，而不是「🎉 恭喜你完成啦！」。

│ 驾驶舱 │ 收录 ⑥ │ 任务 │ 日程 │ 备忘 │ 时间线 │ 回收站 │

### 5.1 驾驶舱（dashboard）— 首页

**回答的唯一问题**：*今天我应该先做什么？*

**首屏必须包含的 5 块**（原型第 216–245 行）：

```text
┌─ 今日主题 ────────────────────────────────────┐
│ 早上好 / 下午好（按当前时间变化）                 │
│ 今日主题：[限流方案定稿]            [设定]      │
└──────────────────────────────────────────────┘
┌─ 今日指标（4 个数字）──────────────────────────┐
│ 待整理 4 │ 今日日程 3 │ 逾期 1 │ 番茄 2        │
└──────────────────────────────────────────────┘
┌─ 今天要处理的 Top3 ───────────────────────────┐
│ ⚠ 支付网关 MR 代码评审       已逾期 1 天   [完成]│
│   阻塞他人 · 回复业务方日配额口径疑问           │
│   ...                                          │
└──────────────────────────────────────────────┘
  今日日程（时间轴）   │   今日任务（清单）
```

**关键规则**：

- **逾期任务置顶且标红**（红 `#A32D2D`），不管它原本的优先级
- Top3 由**规则引擎**计算，排序权重固定为：**逾期 > 阻塞他人 > 临近截止 > 深度工作标记**
- **每条建议必须带可解释的理由**（`reason` 字段），例如「已逾期 1 天」「阻塞他人 · 小李等了 2 天」。禁止出现无法解释的推荐
- 完成后给一句克制的正向反馈，并写入时间线（`praise` 类型）
- 首屏一次请求拿全所有数据（`GET /api/v1/dashboard/today`），**禁止首页发 5 个请求拼装**，本地加载必须 ≤ 1s

**API**：`开发文档-Java8版.md` §4.3

### 5.2 收集箱（inbox）— 零摩擦录入

> **2026-09-12 变更：「收集箱」与「整理确认」已合并为「收录」一个页签。**
> 点「收录」即连续完成「入库 + 整理」两步（`POST /inbox` 紧接 `POST /inbox/classify`），
> 用户不必再单独点一次「开始整理」；整理结果（待确认卡）与收录输入框同页展示，
> 整理失败的条目落在同页的「待整理」区，可逐条重试。导航里不再有「收集箱」页签，
> 回收站里的 `inbox` 类型也显示为「收录」。
> 下面 §5.2 / §5.3 仍分两节保留，是为了说明**两层职责**（入库与状态机 / 判定与确认），
> 界面上一页完成。
>
> 同日起：**收录整理的日期默认今天**。待确认卡的日期框由前端**预填今天**
> （整理器抽出日期则用抽出的；用户可改，清空仍表示「时间待定」，见 US-4.2）；
> 一键批量确认没有表单可填，由后端在抽不出日期时补今天，两条路径结果保持一致 ——
> 否则批量生成的条目没有日期，既不进驾驶舱今日清单、也不在任何按日视图里露出，
> 表现就是「点了生成却哪儿都找不到」。

**回答的唯一问题**：*脑子里冒出来的事，往哪儿扔？*

**交互契约（不可妥协）**：

| 规则 | 要求 |
|---|---|
| 录入路径 | 光标默认已在输入框 → 打字 → 回车 → 完成 |
| 录入耗时 | 从有想法到落库 **≤ 10 秒** |
| 字段要求 | **只要求内容**，不要求分类、日期、优先级 |
| 连续录入 | 提交后输入框**自动清空并保持聚焦**，可连续录入 10 条 |
| 反馈 | 轻提示（toast）「已收录」，不弹窗、不跳页 |

**列表规则**：

- 按创建时间**倒序**（最新的在最上面）
- 每条显示：内容原文、来源（web / wecom 徽标）、状态、创建时间
- 支持软删除（`deleted=1` 标记删除 + `deleted_at` 记录删除时刻，不物理删除）
  - ✅ **US-1.5「30 天内可恢复」已实现**（2026-09-11）：删除只是把记录移入「回收站」页签
    （`GET /api/v1/trash`），30 天内可一键恢复（`POST /api/v1/trash/{type}/{id}/restore`），
    超过 30 天不再列出、也不能恢复。表结构见 `V7__soft_delete_timestamp.sql`。
  - 删除时刻取 `COALESCE(deleted_at, updated_at, created_at)`：V7 之前删掉的历史记录没有
    `deleted_at`，靠 `updated_at` 兜底——否则一次迁移就把它们直接变成「不可恢复」。
  - 恢复只翻转 `deleted=0` 并清空 `deleted_at`，内容与原有的日期/分组/状态原样保留
    （待定日程恢复后仍是待定，不会被恢复动作塞上一个日期）。
  - 因为删除已经可以撤销，软删**不再弹二次确认**（设计规范 §8.2 的放宽条件已满足）；
    只有时间线的物理删除仍需确认。
  - 历史教训：「可恢复」这句话在 2026-09-11 之前是**没有出口的空承诺**——只有
    `WHERE deleted=0` 的过滤，没有恢复接口、界面上也没有任何入口，用户按文档去找回收站只会扑空。
    **写「可恢复」之前先确认恢复路径真的存在**。

**状态机（4 态）** — 这是收集箱的核心，字段 `status`：

```text
                  ┌──────────┐
     录入 ──────► │ pending  │  待整理
                  └────┬─────┘
                       │ 触发整理（手动点 / 每日 16:30 自动）
                       ▼
                  ┌──────────┐   置信度 < 0.70
                  │processed │◄────────────── 标「待人工确认」
                  │ 已整理    │                 不自动生成实体
                  └────┬─────┘
                       │ 用户确认
                       ▼
                  ┌──────────┐
                  │ archived │  已归档（已生成任务/日程/备忘）
                  └──────────┘

        AI 调用失败 ──► failed（可一键重试，原始内容绝不丢失）
```

**API**：`开发文档-Java8版.md` §4.4

### 5.3 整理确认（classify）— 每天 15 分钟清空

> 入口已并入「收录」页（见 §5.2 开头的 2026-09-12 变更说明）：收录后自动触发一次整理，
> 结果直接呈现在同页的「待确认」区。本节的判定逻辑与确认规则不变。

**回答的唯一问题**：*这一堆原始话，哪些是任务、哪些只是备忘？*

**流程（必须 ≤ 3 次点击/条）**：

```text
① 点「整理」按钮（或等每天 16:30 自动触发）
        ↓
② 系统逐条给出判定：类别 + 抽取的字段 + 置信度
   ┌─────────────────────────────────────────┐
   │ 明天下午3点约业务方对齐Q4需求评审           │
   │ ──► [日程] 置信度 0.91                    │
   │     标题：与业务方对齐 Q4 需求             │
   │     时间：明天 15:00                      │
   │        [确认]  [改分类]  [忽略]           │
   └─────────────────────────────────────────┘
        ↓
③ 点「确认」→ 生成正式实体（任务/日程/备忘），条目归档
```

**四条硬规则**：

1. **置信度 < 0.70 的条目标「待人工确认」，绝不自动生成实体。** 宁可让用户多点一下，也不能制造错误数据
2. **改分类后字段表单联动切换**：从"任务"改成"日程"，表单要从【优先级+截止日】变成【时间+时长】
3. **确认生成实体是一个事务**：要么同时更新 `inbox_item.status` 并插入 task/event/memo，要么全回滚。不允许出现"已归档但没生成任务"的孤儿状态
4. **整理失败绝不能丢数据**：AI 调用失败只把状态置为 `failed`，原文保留，支持一键重试

**AI 是可选的**：

- 未配置 AI 时 → 隐藏「整理」按钮，**其余功能 100% 可用**
- 配置了但调用失败 → 回退到**本地规则引擎**（原型中 `aiClassify()` 的 Java 移植版），并标注「本地规则」
- 后端完全不可用时 → 前端保留的规则引擎继续工作

**API**：`开发文档-Java8版.md` §4.4（`POST /inbox/classify`、`POST /inbox/{id}/confirm`、`POST /inbox/{id}/reclassify`）

### 5.4 任务（task）— 追踪要完成的事

**状态机（4 态，字段 `status`）**：

```text
  ┌──────┐  开始    ┌───────┐  完成   ┌───────┐
  │ todo │ ───────► │ doing │ ──────► │ done  │
  │ 待办 │ ◄─────── │ 进行中│         │ 已完成│
  └──┬───┘   退回   └───┬───┘         └───────┘
     │                  │
     └────────┬─────────┘
              │ 取消
              ▼
         ┌─────────┐
         │canceled │  已取消
         └─────────┘
```

- 点击任务左侧圆形按钮**循环切换** todo → doing → done → todo
- 状态为 `done` / `canceled` 的任务默认不在主列表显示，可筛选查看

**优先级 P0–P3**：

| 优先级 | 含义 | 颜色 |
|---|---|---|
| P0 | 今天必须完成 | 红 |
| P1 | 本周内 | 琥珀 |
| P2 | 有空做 | 蓝 |
| P3 | 有生之年 | 中性灰 |

**三个特有属性**（这是本产品相对通用待办的差异点）：

| 属性 | 作用 |
|---|---|
| `deep`（深度工作） | 标记后，驾驶舱优先建议把它排进日程里的**深度块**时段 |
| `blocking`（阻塞他人） | 标记后，驾驶舱排序权重仅次于逾期，reason 显示"阻塞他人" |
| `postponed`（顺延次数） | 每次顺延 +1。**顺延 ≥ 3 次的任务必须在驾驶舱明确提示**，因为它大概率是被无限拖延的事 |

**顺延行为**：点「顺延」→ `due_date` +1 天，`postponed_count` +1。逾期任务在驾驶舱置顶标红，并显示逾期天数（查询时计算，不落库）。

**来源回溯**：`source_inbox_id` 保留 originating 收集箱条目，任务详情可看到"来自：微信 · 9月5日 10:02"。

**API**：`开发文档-Java8版.md` §4.5

### 5.5 日程（schedule_event）— 时间被怎么占了

- 三种类型：`meeting`（会议）、`deep_block`（深度工作块）、`other`
- **按周展示**（2026-09-13 起，见 `docs/日程周视图设计.md`）：纵向三条周条
  「下一周 / 本周 / 上一周」，本周居中；**任何时刻只有一条展开**（点周头切换，其余自动收起）。
  每条严格七行（周一→周日），行内卡片按 `start_time` 升序从左往右排，
  没有具体时间的沉到该行最左侧（标「未排时段」）。
  「回到本周 / ↑ / ↓」挂在**当前展开的那一条**的周头右端。
  检索命中全部日期时退回平铺列表（周网格套不住跨月的命中）。
- **重复日程（「每周 X」）**：收录里写「每周三下午三点开周会」时，会一次生成**连续 4 周**的日程
  （卡片上带「每周」标）。每一期都是**独立**日程 —— 想改其中一期的时间，不会动到其余几期。
- **待定时间区**：暂时定不下日期的日程（`event_date` 为空）不硬塞进某一天，单独成列，补上日期即归队
- **冲突检测**：时间重叠时给出**警告但不阻止**（用户可能有背靠背会议，强制阻止体验很差）。
  这也是周视图**不做「按时间比例定位」**的原因之一：比例视图里重叠卡片必然互相遮挡

**与任务的联动**：标记为 `deep=true` 的任务，驾驶舱会建议排在 `deep_block` 时段内。这是任务模块和日程模块唯一的耦合点，不要过度设计成自动排程。

**API**：`开发文档-Java8版.md` §4.6

### 5.6 备忘（memo）— 反复查的信息

**定位**：不是笔记，是**速查库**。判断标准：这条信息你会不会查第二次？会 → 备忘；不会 → 别存。

**典型内容**：班车时刻表、VPN 地址、运维值班电话、奶粉型号、要买的清单、值得收藏的链接。

**四个核心能力**：

| 能力 | 规则 |
|---|---|
| **空间切换** | 全部 / 工作 / 生活三选一。**界面约束：全部独占首行，工作/生活次行并列** |
| **全文检索** | 范围覆盖标题、内容、标签、链接，结果 ≤ 300ms |
| **置顶** | 高频查阅项（班车表）排最前 |
| **归档** | 失效项（买完的东西）归档，默认隐藏，可筛选查看、可恢复 |

**自动能力（降低录入摩擦）**：

- 内容里的 URL **自动提取**为可点击链接，同时存入 `url` 字段
- 按关键词**自动打标签**：家庭采购 / 通勤 / 链接收藏 / 运维等
- 自动判定工作/生活分组（可手动一键切换：点卡片上的分组徽标）

**视觉约束（已定的设计规范，不要改）**：

> 空间容器可以用主题色表达氛围（全部=晨雾蓝 `#eef4fa`、工作=玉簪青 `#eaf3ed`、生活=暖纸珊瑚 `#fbede6`），但**记录卡统一使用中性白色载体**，只用分组徽标和标签色区分工作/生活。
> **原因**：主题色大面积染色会让"新增记录"按钮和卡片本身视觉过载，反而看不清内容。

**API**：`开发文档-Java8版.md` §4.7

### 5.7 时间线（timeline）— 我之前干了什么

- 按**自然日分组**的操作流水，倒序
- 记录的事件类型：`inbox`（收录）、`task`（任务完成/删除）、`plan`（设定主题）、`pomo`（完成番茄）、`praise`（完成任务的正向反馈）
- 用途是**回顾感**，不是审计日志。文案要像日记，不像系统日志：
  - ✅ 「完成任务「梳理限流方案初稿」— 漂亮，这事终于落地了」
  - ❌ 「TASK_STATUS_CHANGED id=42 from=todo to=done」
- 上限 500 条，超出截断
- **支持单条删除**：鼠标悬停某条记录卡片时，右上角浮现小垃圾桶图标，点击即删除该条并自动刷新列表
  - 时间线是操作流水而非正式实体，按 R6 规则**物理删除**（不走软删除），删了不可恢复
  - 删除不存在的记录返回 `404 / code 1001`，前端提示「这条时间线记录不存在或已经被删除」
  - **必须二次确认**（2026-09-11 补上，2026-09-11 晚复核）：这是全应用**唯一不可逆**的删除，
    实现回收站后它是**唯一**仍需要确认的删除动作（软删都能在回收站捞回来，见 §5.2 / §8.2）；
    确认文案要明确「不走软删除、不经过回收站、删了无法恢复，与任务/备忘的删除不同」。
    `title` / `aria-label` 也写明「永久删除…无法恢复」。
  - 触屏（`@media(hover:none)`）下图标常显，命中区从 22px 放大到 36px 并同步加大卡片右侧留白，
    避免误触（桌面端保持 22px，有 hover 提示、指针精度高）。

**API**：`开发文档-Java8版.md` §4.9

### 5.8 番茄钟（pomodoro）— 悬浮组件，不是独立视图

**位置**：右下角常驻入口，点击弹出全屏遮罩计时器。

- 三种模式：专注（默认 25min）/ 短休（5min）/ 长休（15min），时长**可配置**
- 结束时：**页面标题闪烁 + 蜂鸣提示**（原生 AudioContext，不用音频文件，避免包体变大）
- 每个完成的番茄写入 `pomodoro` 表 + 时间线

**视觉例外（重要）**：

> 番茄钟**保留独立的深色科幻主题，不跟随全局晨雾蓝换肤**。
> 这是刻意为之：计时器需要一个与外部隔绝、让人静下心的暗色环境，浅色会削弱沉浸感。

## 6. 核心用户旅程（4 条主线）

### 旅程 1：碎片录入 → 整理 → 落地（**主链路，必须丝滑**）

```text
微信收到「帮我看下这个方案」
   │
   ├─ 打开工作台（浏览器基本常年开着）── 3s
   ├─ 光标已在输入框，粘贴/打字 ──────── 5s
   ├─ 回车 ──────────────────────────── 0s  → "已收录"
   ↓
（当天 16:30 自动触发整理，或手动点）
   ├─ 系统在「整理确认」给出判定：任务 / 置信度 0.86
   ├─ 扫一眼，点「确认」──────────────── 1 次点击
   ↓
生成任务，出现在驾驶舱的今日任务中
```

**量化目标**：单条录入 ≤ 10 秒；确认 ≤ 3 次点击/条；收集箱日清空率 ≥ 90%。

### 旅程 2：每天开工

```text
早上打开工作台
  → 驾驶舱直接告诉我：1 个逾期（标红置顶）+ 2 个今天要做
  → 设定今日主题「限流方案定稿」（2026-09-20 下线，驾驶舱已无此入口）
  → 点开番茄钟，专注 25 分钟
  → 完成，时间线记一笔
```

### 旅程 3：速查信息

```text
「班车几点来着？」
  → 切到备忘 → 搜索框输入「班车」或靠置顶直接看到
  → 300ms 内出结果
```

### 旅程 4：周末清理

```text
打开任务页 → 筛出「已取消」和「已完成」→ 确认无误
打开备忘 → 把买完的东西归档
点「立即备份」→ data/backups/ 生成一份快照
```

## 7. 业务规则汇总（AI 实现时逐条对照）

| # | 规则 | 值 / 行为 |
|---|---|---|
| R1 | 整理置信度阈值 | `< 0.70` → 标「待人工确认」，不自动生成实体 |
| R2 | 驾驶舱 Top3 排序权重 | 逾期 > 阻塞他人 > 临近截止 > 深度工作 |
| R3 | 推荐理由 | 每条**必须**带 `reason` 字符串，禁止无理由推荐 |
| R4 | 逾期天数 | 查询时用 `julianday` 计算，**不落库** |
| R5 | 顺延 | `due_date` +1 天 + `postponed_count` +1；≥3 次在驾驶舱明确提示 |
| R6 | 删除 | 用户可管理的正式实体（收集箱、任务、日程、备忘、知识笔记）使用软删除；操作流水、配置、关联表按业务规则处理 |
| R7 | 日程冲突 | 警告但**不阻止** |
| R8 | 备忘检索 | 覆盖标题 / 内容 / 标签 / 链接四个字段 |
| R9 | 时间线上限 | 500 条，超出截断 |
| R10 | 首页请求 | 一次 `GET /dashboard/today` 拿全，**禁止多请求拼装** |
| R11 | 自动备份 | 每日 02:00，保留最近 14 份 |
| R12 | AI 降级 | 无配置 → 隐藏入口；调用失败 → 回退本地规则引擎并标注 |
| R13 | 时间字段 | **一律 Java 侧生成**（SQLite 的 `localtime` 取 OS 时区，与 JVM 时区可能不一致，会导致同一页面两个时间对不上） |
| R14 | 备份方式 | **必须 `VACUUM INTO`**，禁止直接复制 db 文件（WAL 模式下会拿到不一致快照） |

> R13、R14 是踩过坑的规则，实现时不要自作聪明改掉。技术细节见 `开发文档-Java8版.md` §3.2 / §6.4。

| 删除 | **软删除免二次确认，不可逆动作必须确认**（2026-09-11 实现回收站后按此规范放宽）。<br>① 任务 / 日程 / 备忘 / 知识 / 收集箱：只是移入回收站、30 天内可恢复 → 不弹确认，但 **toast 必须说清「已移入回收站，30 天内可恢复」**，否则用户不知道去哪儿找回来，等于没有撤销。<br>② 时间线（`activity_log`）：按 R6 走物理删除、不进回收站，是**全应用唯一不可逆**的删除 → **必须二次确认**，且文案必须写明「无法恢复」。<br>历史沿革：原规范「软删除不给二次确认（可恢复）」的**前提是能恢复**；2026-09-11 之前站内并没有恢复入口，前提不成立，当时的做法是「一律确认」并写清「需要时得手工改库找回」。回收站落地后，该前提成立，遂回到「软删免确认、仅不可逆动作确认」。<br>检查脚本按这三条钉住：硬删分支必须有 `confirm(` 且含「无法恢复」、软删分支不得有 `confirm(` 且 toast 必须含「回收站」。 |

| 报错 | 中文、说人话、给出下一步。例如「端口 18080 被占用，点这里查看是哪个程序」 |

## 9. 边界：明确不做的事

### 9.1 功能边界（版本 A）

| 能力 | 版本 A | 原因 |
|---|---|---|
| 驾驶舱 / 收集箱 / 整理 / 任务 / 日程 / 备忘 / 时间线 / 番茄 | ✅ 完整 | 纯本地 |
| AI 整理 | ⚠️ 可选 | 需填 LLM 配置；不填则隐藏入口，其余照常 |
| Obsidian 同步 | ⚠️ 可选 | 需选本地 Vault 路径；**知识助手 UI 在版本 A 移除** |
| 企业微信接入 | ❌ | 需公网 HTTPS 回调 + 自建应用凭证 |
| 语音 ASR | ❌ | 需外部 ASR 服务。改为文字录入 |
| 手机/远程访问 | ❌ | 需内网穿透或 HTTPS 域名 |
| 多用户 / 协作 / 权限 | ❌ | 单用户产品 |
| 数据云同步 | ❌ | 违反"本地优先" |

### 9.2 不要自作主张加的东西

- ❌ 用户系统、角色、权限 → 单用户
- ❌ 标签管理页、分类树管理 → 分类是固定的四类，不需要让用户自定义
- ❌ 周报/月报生成器 → P3，超出 MVP
- ❌ 数据可视化图表墙 → 驾驶舱只要 4 个数字 + Top3
- ❌ 暗色模式切换 → 全局不做（番茄钟的深色是固定的，不是主题切换）
- ❌ 国际化 → 只有中文

### 9.3 交付时必须告诉同事的三件事（写进 `使用说明.txt`）

1. **不要把程序放在桌面或 OneDrive 目录** — 网盘实时同步会锁住 `workbench.db-wal`，导致数据库损坏
2. **数据全在 `data/` 目录** — 换电脑/重装系统，复制整个 `data/` 即可
3. **关掉程序要点「停止工作台.cmd」** — 直接关窗口也能安全退出（有优雅停机），但不推荐

## 10. 数据视角的地图（不重复 DDL）

12 张表按业务分组，**完整 DDL 见 `开发文档-Java8版.md` §3.3**，这里只讲业务含义：

```text
【录入】
  inbox_item        收集箱条目（原始话 + AI 判定 + 状态）
  wechat_msg_log    企业微信消息流水（版本 B 才用，表先建）

【正式实体】
  task              任务（状态 / 优先级 / 截止 / deep / blocking / postponed）
  schedule_event    日程（会议 / 深度块 / 其他）
  memo              备忘（标题 / 内容 / 标签 / URL / 空间 / 置顶 / 归档）
  knowledge_note    知识笔记（版本 A 隐藏，表保留）

【活动记录】
  pomodoro          番茄记录
  activity_log      时间线流水
  daily_plan        每日计划（主题 + 完成率）
  daily_plan_item   每日计划项

【系统】
  ai_job            AI 调用记录（耗时 / token / 成败）
  app_config        配置（含 initialized 标记，决定首次配置向导）
```

**三条数据规则**：

1. **`inbox_item` → 正式实体是 1 : 0..1**，通过 `source_inbox_id` 回溯，永不删除原条目（软删 + 归档）
2. **用户可管理的正式实体表**（`inbox_item`、`task`、`schedule_event`、`memo`、`knowledge_note`）使用 `deleted` 软删；`activity_log` / `ai_job` 等流水表按保留策略清理，`app_config` 与关联表不需要软删
3. **`app_config.initialized`** 决定首次访问是否跳转配置向导；构建发布包时**必须清空这个标记**，否则同事打开就是你的账号

## 12. 容易跑偏的地方（踩过或高概率踩）

| # | 误解 | 正确做法 |
|---|---|---|
| 1 | 把收集箱当成待办列表，要求录入时选分类/日期 | 收集箱**只存原始话**，归类在"整理确认"做。这是 P1 原则 |
| 2 | 用 Hibernate/JPA 映射 SQLite | 用 **JdbcTemplate**。Hibernate 5 无官方 SQLiteDialect，会浪费半天 |
| 3 | 时间用 SQLite 的 `datetime('now','localtime')` | **Java 侧生成**。OS 时区 ≠ JVM 时区，同一页面会显示两个不一致的时间 |
| 4 | 备份直接复制 `workbench.db` | 用 **`VACUUM INTO`**。WAL 模式下直接拷贝会拿到不一致快照 |
| 5 | 忘记 SQLite 默认关闭外键 | 连接初始化时必须设 `PRAGMA foreign_keys=ON`（开发文档 §3.7 用 `SQLiteConfig` API 逐连接设置） |
| 6 | 把个人数据打进发布包 | 构建脚本有硬校验：清空 `data/`、清 `app_config.initialized`、清 AI Key |
| 7 | 认为"AI 整理"是核心功能 | **它是可选增强**。不配 AI，产品必须 100% 可用 |
| 8 | 给每个视图加独立的 `renderXxx()` 并互相调用 | 保持 `render()` 为唯一刷新入口。互调会栈溢出（开发文档 §7.5） |
| 9 | 用 `Join-String` 写 PowerShell | Windows 自带 PowerShell 5.1 没有这个命令，用 `-join ','` |
| 10 | `.cmd` 和 `.ps1` 用同一种编码 | `.cmd` 用 **GBK**，`.ps1` 用 **UTF-8 with BOM**，否则中文必乱码 |

## 13. 产品验收：用户视角的 8 条

技术验收见 `开发文档-Java8版.md` §10。这里是**产品视角**——一个真实同事能不能用起来：

| # | 场景 | 通过标准 |
|---|---|---|
| 1 | 新人首次打开 | 看到配置向导，只有 3 个必填项，30 秒内能进主界面 |
| 2 | 第一次录入 | 不需要看说明书，就知道在输入框打字回车 |
| 3 | 首次整理 | 4 条示例数据能被正确分类，至少 3 条置信度 ≥ 0.70 |
| 4 | 断网使用 | 拔掉网线，除了 AI 整理，所有功能正常 |
| 5 | 逾期感知 | 打开首页第一眼就看到"有 1 件事逾期了"，且是红色的 |
| 6 | 找回信息 | 想找班车时刻表，10 秒内找到 |
| 7 | 重启后 | 数据还在，任务与顺延次数还在 |
| 8 | 想带走数据 | 复制 `data/` 到另一台电脑，完整恢复 |

**一句话验收**：把这个包给一位不用待办 App 的同事，两周后他还在用——这才算成功。
